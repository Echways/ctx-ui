# Конструктор серверов

Конструктор это расширение панели. Оно собирает в панели MCP-серверы на FastMCP,
запускает каждый в своём изолированном Docker-контейнере и подключает его как
HTTP-инбаунд, поэтому сервер доходит до клиентов так же, как любой другой. Токены,
лимиты, журнал, метрики и OAuth работают для собранных серверов без дополнительных
настроек.

[English](../builder.md) · [Русский](builder.md)

Конструктор не входит в ctx-ui. Без него в панели нет ни следа от него, а основной
образ и установка через systemd обходятся без Python и Docker.

## Установка

Нужны Docker Engine 29 или новее на хосте, установленный ctx-ui (systemd или Docker)
и root.

```bash
curl -fsSL https://github.com/Echways/ctx-ui/releases/latest/download/builder-install.sh | sudo bash
```

Установщик сам определяет способ установки ctx-ui, проверяет Docker и `SHA256SUMS`
релиза и, если что-то не так, останавливается до любых изменений. Затем он генерирует
токен Runner, поднимает контейнеры, записывает настройки
`CtxUi__Extensions__builder__RunnerUrl`, `CtxUi__Extensions__builder__RunnerIngressUrl`
и `CtxUi__Extensions__builder__RunnerToken`, ставит расширение и перезапускает ctx-ui.
Токен и адрес руками задавать не нужно.

| Параметр | Что делает |
| --- | --- |
| `--version <v>` | ставит указанный релиз вместо последнего |
| `--remove` | удаляет контейнеры с меткой `ctx-ui.builder` и расширение; ctx-ui продолжает работать |

```bash
curl -fsSL https://github.com/Echways/ctx-ui/releases/latest/download/builder-install.sh \
    | sudo bash -s -- --version 0.2.0
```

Для обновления выполните команду ещё раз: токен и собранные серверы сохраняются. В
навигации панели появляется раздел «Конструктор». Если Runner недоступен, раздел
показывает причину и эту команду.

Установщик скачивает три образа для `amd64` и `arm64`:
`ghcr.io/echways/ctx-ui-builder-runner`, `ghcr.io/echways/ctx-ui-builder-runtime` и
`ghcr.io/echways/ctx-ui-builder-egress`. Rootless Docker и Podman не поддерживаются.

## Первый сервер за пять минут

1. Откройте «Конструктор» > «Серверы» и нажмите «Новый сервер». Введите имя и слаг,
   затем «Создать». Слаг потом не меняется. Можно начать и с документа OpenAPI
   («Документ OpenAPI (необязательно)»), и с архива проекта.
2. Добавьте инструмент. Один из двух способов:
   - нажмите `+` рядом с «Инструмент формой»: выберите метод, путь, напишите описание
     и параметры, нажмите «Сохранить». Такие инструменты вызывают HTTP API, поэтому
     сначала задайте адрес API в «Настройки» > «API»;
   - нажмите `+` рядом с «Инструменты кодом», введите имя инструмента и нажмите
     «Добавить». Инструмент открывается с рабочей заготовкой.
3. Нажмите «Опубликовать». Черновик сохраняется сам, а опубликованное не меняется,
   пока вы не опубликуете. Сборка идёт в фоне, ход виден в статусе в шапке.
4. Откройте «Проверка», выберите инструмент, заполните аргументы и нажмите «Вызвать»:
   это настоящий MCP-вызов.
5. После первой успешной публикации открывается панель подключения (позже её открывает
   «Подключить»). Выберите слаг инбаунда и клиентов, которые получат доступ, и
   подтвердите. Панель покажет адрес инбаунда. Передайте его клиенту обычным способом.

«Собрать без активации» в меню публикации собирает версию и позволяет вызвать её в
«Проверка», пока она не стала активной.

## Из чего состоит сервер

Сервер это обычный проект FastMCP:

```
fastmcp.json     зависимости, версия Python, транспорт
main.py          общий для всех серверов, не редактируется
builder.json     ресурсы и промпты, созданные формой
openapi.json     инструменты, созданные формой или импортом
mcp/*.py         ваш код: @tool, @resource, @prompt
```

- **Инструмент формой** редактирует одну операцию в `openapi.json`: метод, путь,
  описание, параметры, необязательный пример ответа. «Импорт OpenAPI» читает
  JSON-документ по адресу или из вставленного текста и даёт отметить нужные операции;
  по умолчанию не выбрана ни одна. YAML и Swagger 2.0 не принимаются.
- **Инструмент кодом** это Python-файл в `mcp/`. «Превратить в код» один раз
  превращает инструмент формой в файл, обратного пути нет.
- **Ресурсы и промпты** создаются формами. `{name}` в шаблоне промпта становится
  обязательным аргументом.
- **Настройки**: базовый адрес и авторизация API (нет, Bearer, заголовок, Basic),
  зависимости (по одному требованию Python в строке), секреты, сеть и лимиты, экспорт.
- **Секреты** только на запись, панель показывает имена. Сервер получает их переменными
  окружения.
- **Версии** перечисляют все публикации с журналом сборки и позволяют откатиться
  кнопкой «Откатить на эту версию». Неудачная публикация помечается как неудачная, а
  активная версия продолжает работать. Удалённые инструменты показываются
  предупреждением.
- **Логи** показывают вывод активной версии и последнюю сборку.

Правка одного кода не ставит пакеты заново: окружение переиспользуется, пока не
изменятся зависимости, версия Python или версия FastMCP. Хранятся последние 5 версий
вместе с окружениями.

## Доступ к сети

Базовая изоляция одинакова для всех серверов и не отключается: сервер работает не от
root, с `cap_drop: ALL` и `no-new-privileges`, на корне только для чтения, с `tmpfs` на
`/tmp` и своим томом `/data`. Данные ctx-ui, Docker socket и соседние серверы ему
недоступны. Лимиты по умолчанию: 512 МБ, 1 CPU, 256 процессов; меняются в «Настройки» >
«Сеть и лимиты».

Один переключатель на сервер, «Сеть»:

| | Только интернет (по умолчанию) | Вся сеть |
| --- | --- | --- |
| Сеть контейнера | своя `internal`-сеть, единственный выход через прокси Squid | обычный bridge |
| Куда можно | HTTP и HTTPS на публичные адреса | любые адреса и порты, включая локальную сеть и базы данных |

В режиме «Только интернет» прокси проверяет адрес назначения после разрешения имени и
отказывает для частных, служебных и link-local диапазонов (это закрывает и метаданные
облака), а также для почтовых портов 25, 465 и 587. Остальные порты на публичных
адресах открыты. Сервер получает `HTTP_PROXY` и `HTTPS_PROXY`; клиент, который их
игнорирует, остаётся без сети. Когда прокси отказал в запросе, «Проверка» и логи
сообщают об этом и ведут к настройке.

«Вся сеть» требует подтверждения со списком того, что становится доступно. Соседние
серверы и данные ctx-ui недоступны в обоих режимах.

### Что остаётся незакрытым

- **Общее ядро.** Контейнеры не защищают от уязвимости ядра. Переменная
  `BUILDER_RUNTIME=runsc` у Runner запускает серверы в gVisor, если он установлен на
  хосте. По умолчанию выключена.
- **Компрометация Runner при rootful Docker равна root на хосте.** Поэтому сервис
  маленький, не исполняет код пользователя и не принимает параметров запуска контейнера.
- **Администратор пишет код и видит его результат.** Секреты сервера доступны его коду,
  а значит и администратору. Это не граница между администраторами: все, кто входит в
  панель, видят и правят все серверы.
- **Логи не маскируются.** Если код напечатает секрет, он окажется в логах панели.

## Ручная установка

Нужна, если скрипт не подходит. Понадобятся папка `deploy/builder` релиза, например из
репозитория по тегу `v<версия>`, и архив `builder-<версия>.zip` со страницы релиза.

Установка через systemd:

```bash
export CTX_UI_VERSION=0.2.0
export CTXB_RUNNER_TOKEN=$(openssl rand -hex 32)
docker compose -f deploy/builder/compose.yaml up -d
```

Это проект `ctx-ui-builder`. Runner слушает `127.0.0.1:8091` (управление) и
`127.0.0.1:8090` (серверы). Добавьте в `/etc/ctx-ui/ctx-ui.env`:

```
CtxUi__Extensions__builder__RunnerUrl=http://127.0.0.1:8091
CtxUi__Extensions__builder__RunnerIngressUrl=http://127.0.0.1:8090
CtxUi__Extensions__builder__RunnerToken=<тот же токен>
```

```bash
sudo ctx-ui extension install builder-0.2.0.zip
sudo systemctl restart ctx-ui
```

Установка через Docker, в каталоге `ctx-ui`. Порядок файлов важен, оверлей идёт
последним: он сохраняет имя проекта `ctx-ui`, подключает ctx-ui к сети Runner и не
публикует портов:

```bash
docker compose -f deploy/docker/compose.yaml -f deploy/builder/compose.yaml -f deploy/builder/compose.docker.yaml up -d
```

`CTXB_RUNNER_TOKEN` добавьте в `.env` рядом с `CTX_UI_VERSION`. Настройки идут в
`environment` службы `ctx-ui`:

```
CtxUi__Extensions__builder__RunnerUrl=http://10.212.0.2:8091
CtxUi__Extensions__builder__RunnerIngressUrl=http://10.212.0.2:8090
CtxUi__Extensions__builder__RunnerToken=<тот же токен>
```

Затем выполните `ctx-ui extension install` внутри контейнера или смонтируйте
распакованное расширение (см. [расширения](extensions.md#установка-обновление-удаление))
и перезапустите его.

Остальные настройки Runner, в `environment` службы `runner`: `RUNNER_SUBNET_POOL`
(подсети сетей серверов, по умолчанию `10.213.0.0/16`) и `BUILDER_RUNTIME`.

## Удаление и очистка

- Удаление инбаунда на странице инбаундов не удаляет сервер. Страница сервера после
  этого покажет «Не подключён», и его можно подключить снова.
- «Удалить сервер» у подключённого сервера просит подтверждения, где показаны инбаунд и
  число его клиентов, и удаляет сервер, все его версии, инбаунд и его связи с клиентами.
  Отменить это нельзя.
- `docker volume prune -a` удаляет тома конструктора, в том числе маркеры активации и
  тома `/data` серверов. Не запускайте его на хосте с серверами конструктора.
- `docker system prune` удаляет остановленный контейнер, в том числе активного сервера,
  если он был остановлен. Запустите его снова из панели («Запустить снова»).
- После перезапусков у сервера могут остаться контейнеры без маркера активации. Они не
  получают маршрута и остаются до следующей активации или удаления сервера, поэтому
  такие контейнеры могут накапливаться.
- Удаление расширения, в том числе с `--purge`, не останавливает контейнеры. Серверы и
  инбаунды продолжают работать. `builder-install.sh --remove` удаляет контейнеры с
  меткой `ctx-ui.builder` вместе с расширением.
- Пока Runner недоступен, черновики редактируются, а публикация нет, и вызовы клиентов к
  собранным серверам падают до его возвращения.
- `ctx-ui backup` покрывает черновики, версии и секреты конструктора (данные
  расширения), но не тома `/data` серверов.

## API для CI

У расширения есть эндпоинты под `/<panel>/extensions/builder/`. Нужен API-ключ в
`Authorization: Bearer ctxk_…`, как в [REST API](README.md#rest-api).

| Запрос | Результат |
| --- | --- |
| `GET servers` | список: `id`, `slug`, `name`, `networkAccess`, `state`, `activeRelease`, `buildingRelease`, `inboundId` |
| `GET servers/{id}` | сервер с лимитами, базовым адресом, именами секретов и версиями |
| `POST servers/{id}/publish` | запускает публикацию, `202` с `{"release": n}` |
| `POST servers/{id}/rollback/{n}` | активирует версию `n`, `202` с `{"release": n}` |
| `GET servers/{id}/export` | проект архивом `tar.gz` |

У `publish` есть необязательный параметр запроса `mode`: `Activate` (по умолчанию) или
`BuildOnly`. Вызов возвращается сразу; опрашивайте `GET servers/{id}` и читайте
`releases[].status`. Ошибки приходят как `application/problem+json`: 404 нет такого
сервера или версии, 409 идёт сборка, сервер удаляется или версию нельзя восстановить,
503 настройки Runner заданы не полностью.

```bash
curl -X POST -H "Authorization: Bearer ctxk_..." \
    "https://mcp.example.com/<secret>/extensions/builder/servers/$ID/publish?mode=BuildOnly"
```

## Экспорт и запуск вне панели

«Экспорт» > «Скачать архив» отдаёт проект в `tar.gz`. Он запускается обычным FastMCP,
без панели:

```bash
fastmcp run fastmcp.json
```

Проекту с `openapi.json` нужна переменная `BUILDER_BASE_URL`, а для авторизации
`BUILDER_API_HEADERS`, JSON-объект с заголовками:

```bash
BUILDER_BASE_URL=https://api.example.com \
BUILDER_API_HEADERS='{"Authorization": "Bearer ..."}' \
fastmcp run fastmcp.json
```

Значения секретов в архив не попадают; задайте их переменными окружения там, где вы его
запускаете. Тот же архив можно импортировать при создании сервера.
